# Implementation Plan: Instruments Management

**Branch**: `014-instruments-management` | **Date**: 2026-09-18 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/014-instruments-management/spec.md`

## Summary

Replace hardcoded instrument definitions with a database-driven `Instrument` model managed via Django Admin. The admin selects a pitch (one of 12 chromatic notes); the transposition offset is computed automatically. A data migration seeds the four original instruments and migrates existing `MelodyTab` records from string references to foreign keys. Instrument deletion cascades to tabs with a last-tab Piano fallback. The frontend fetches instruments dynamically from a new API endpoint.

## Design Decisions

### D-001: Instrument Model in `melodies` app

The `Instrument` model is placed in `backend/melodies/models.py` alongside `Melody` and `MelodyTab` because instruments are tightly coupled to melody tabs. A separate Django app would add unnecessary complexity.

### D-002: Pitch stored, offset computed

The `pitch` field is stored in the database. The `offset` field is also stored (not computed on-the-fly) to allow efficient queries and avoid recomputing on every transposition. The offset is set automatically in the model's `save()` method based on the pitch-to-offset mapping.

### D-003: ForeignKey over CharField

`MelodyTab.instrument` changes from `CharField` to `ForeignKey(Instrument)` for referential integrity, cascade support, and proper relational modeling. See research.md R-002 for full rationale.

### D-004: Public instruments endpoint

`GET /api/instruments/` is public (no auth required) because instrument data is needed to display melody tabs even for shared/public melodies. No sensitive data is exposed.

### D-005: Instrument pitch immutability

Pitch cannot be edited after creation (FR-009). Enforced at the Django Admin level (read-only field on edit form) and at the model level (override `save()` to reject pitch changes on existing records).
